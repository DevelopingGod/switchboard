## How it works

### What the CLIs report (verified 2026-11-21)

| CLI | Where | What Switchboard keeps |
|---|---|---|
| Claude Code 2.1.326 | `rate_limit_event` lines in the run's stream-json output (already in Paperclip's run log) | each window's share used, reset time, allowed or rejected; read while the run streams |
| Codex 0.170.0 | the run's own session file, `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-…-<thread id>.jsonl` | the numbers of the last `rate_limits` record, read by hostprobe after the run |

`usage_windows` (migration 0010) keeps one row per CLI, account and window. Codex names its windows by the length
it reports ("30-day" on the free plan here), and only the windows it reports are shown.

hostprobe's `POST /codex/usage` takes the thread id (a UUID, no paths) and an account name, walks only
`sessions/<year>/<month>/<day>/` without following links, opens only `rollout-*-<id>.jsonl`, reads its last 4 MB and
returns only numbers and a "limit reached" flag. Tests cover traversal ids, symlinked folders and files, the tail
limit, and that nothing else from the file (or `auth.json`) can come back.

**Estimates.** Without a fresh report, a window is our own consumption in it (list price for Claude, tokens for
Codex) divided by a capacity learned from the last report. No calibration, no percentage. Use of the CLI outside
Switchboard only shows up in the CLI's own reports, so an estimate is always labelled.

### The guard

`config/agents.yaml` → `subscription_guard`: at **80%** of a window, light jobs (level 0, or a Run-as-job whose
routing rule isn't `code-heavy`) go to the next agent in the chain; at **100%**, or when the CLI says rejected, every
job does. The preview, Run as job and the job engine use the same check (`jobs.agent_check`).

### Waiting for a reset

A run that ends on a limit (Claude's `rejected` event, Codex's `limit reached`, or the run's error matching
`limit_patterns`) is recorded, then the job goes to `waiting_reset` until the reset the CLI reported (else the
configured window length, marked as an estimate). Nothing else changes: same worktree, same branch, same account. At
the reset the same phase runs again with a note to check `git status`/`git diff` first; the Paperclip wake key gets
an attempt suffix (`…-run-0-a1`). If every agent is window-blocked before a job starts, it waits instead of failing.

- More than `max_auto_wait_h` (12) away: the job asks you (gate `limit`). Approval expiry applies.
- After `max_waits` (3) waits it fails with a plain reason.
- Everything is in the database: a restart in the middle loses nothing (tested, and proved live below).

### Accounts

An extra account is a folder hostprobe creates (`~/.switchboard/accounts/<cli>/<name>`, mode 700). The vendor CLI
writes its own files there: even `claude auth status`, run against the folder, creates `.claude.json`. Switchboard
never reads, copies or moves anything inside it. A run sets only the CLI's own variable (`CLAUDE_CONFIG_DIR` or
`CODEX_HOME`). A job is bound to one account per CLI at create; a chain mixing two accounts of one CLI is refused,
and "Run on another agent" offers other providers only.

### Paid overflow

When you confirm it, the job runs on the `opencode-paid` agent: OpenCode with a provider pointed at LiteLLM. Before
each run the router creates a LiteLLM virtual key (budget = what's left of the job's and the month's paid budget,
only the chosen model, expiring after the job's time limit plus 30 minutes, tags `switchboard-overflow` and
`sb-job-<id>`). hostprobe writes the key to `~/.switchboard/overflow/opencode-paid.key` (file 600, folder 700), and
the agent's stored config holds only `{file:…}`. When the run ends, whatever happened, the key is revoked and the
file removed; a sweep on start and every 5 minutes removes leftovers. The spend log's tags file the cost under the
job. Paperclip has no per-run secret mechanism and keeps every config revision, which is why the key never goes
there.

### Dev-only switches (never in `deploy/.env`; doctor warns)

- `ROUTER_LIMIT_TEST=<cli>:resets_in=<seconds>`: the first run of that CLI in each job ends as if it hit its limit.
- `ROUTER_OVERFLOW_ALLOW_FREE=true`: paid overflow may use a free model (labelled a test), to try the key lifecycle
  without spending money.

## Decisions taken without asking (reversible)

- **One Paperclip agent per Switchboard agent**, not one per (agent, account): the config, including the account's
  variable, is written for every run anyway, and `env` is replaced whole on each write (verified).
- **Light work** is level 0, or a Run-as-job whose rule isn't `code-heavy`; a New job has no rule, so only its level
  counts. The thresholds live in `agents.yaml` (`subscription_guard`), next to the agents, not in `rules.yaml`.
- **Limit hits are shown for the last 30 days** on Metrics, not for the selected range (the quotas view isn't
  range-bound).
- **The waiting job opens on its Timeline**, not the Live log: nothing runs while it waits (this also removed a
  baseline race).
- **The minimum paid budget is $0.05**, because LiteLLM checks a key's budget against an estimate before each call.
