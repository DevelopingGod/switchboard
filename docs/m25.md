## How it works

### Files
- `POST /attachments` (router) takes the raw body with the name in `X-Filename`; the portal's `/api/attachments`
  streams it through after the same-origin checks and a Content-Length cap.
- The type comes from the bytes; the extension must agree. Refused: archives (zip, docx, …), programs, HTML, SVG,
  binary data, unknown text extensions, names that don't match the content. Limits and the allowed lists are in
  `config/attachments.yaml`.
- Images: Pillow (`pillow~=12.3.0`) under a pixel cap, orientation applied, metadata dropped by re-encoding, scaled
  to 2048 px, a 320 px WebP thumbnail. PDFs: pypdf (`pypdf~=6.21.4`), first 50 pages. Text: UTF-8, 200,000
  characters. Extracted text is secret-scanned and stored masked (the local model also gets the masked text).
- Storage (ADR 0016): `~/.switchboard/data/attachments/{staging,threads,jobs}/…`, 0700/0600. Same content twice in a
  chat is stored once. Deleting a chat (or Clear chats) deletes its files; unsent uploads go after 24 h.
- Serving: images inline with a CSP that allows nothing and `sandbox`; everything else is an
  `application/octet-stream` download; `nosniff` always; cross-site reads are refused.

### What the model receives
- Documents: a fenced block after your text (`[Attached PDF “q3.pdf”, 12 pages]`), counted in the context window.
- Images: an OpenAI-style `image_url` part (data URI); LiteLLM converts it per provider. Images of the newest
  image-bearing message are sent; older ones become "[Image “x.png” attached earlier]" (`history_images: 1`).
- Token estimate: Gemini 258 tokens per 768 px tile (one tile up to 384 px), xAI 256 per 448 px tile, others
  `width × height / 750`, labelled an estimate. Text is ~4 characters per token.

### Routing
- Every target is checked for the `vision` tag when there is an image ("Can't read images" otherwise). Rules
  `vision` (`best:vision`) and `long-document` (`best:long-context`) in `rules.yaml` (`when: { attachment: … }`),
  editable in the Rules UI. A code file sets the intent to code. A manual pick that can't read images falls back to
  the vision rule's chain.
- The quota guard counts the attachments: a message that would go over what is left of a provider's token window is
  sent elsewhere first ("This message (≈50,000 tokens with attachments) would go over the minute token limit").
- Ollama models are tagged `vision` from Ollama's own `/api/show` capabilities, so a new local vision model needs no
  config entry. Gemini Flash-Lite is now tagged `vision` (checked live: it read a chart correctly).

### Local vision models (measured 2026-11-22, RTX 3050 4 GB, small profile)

so `qwen2.5vl:3b` was **skipped** and the smaller `qwen3-vl:2b` (1.89 GB) tried instead (5.24 GB pulled in all).

|---|---|---|---|---|
| `qwen3-vl:2b` | 2.34 GB | 1.91 GB (82%) | 5/5 (needs room to answer: with a 40-token limit it answered nothing) | ~2.0 s |

first reply with a private image is slower (a cold load took 7–30 s here), and it is loaded only for private
images. Live: a private chart question was answered "B" by `qwen3-vl:2b` in 3 s once loaded.

### Activity (ADR 0017)
`GET /activity` keyset-pages `requests` on `(created_at, id)`; `/activity/options`, `/activity/{id}` ("Why this?")
and `/activity.csv` (up to 50,000 rows). Titles, summaries and model tests write `requests` rows (kind `aux`,
`test`); the Metrics rollup skips them and keeps counting those calls from their cost rows, so totals don't change.

## Decisions taken without asking (reversible)
- Image token rules live in `config/attachments.yaml` (`image_tokens`), not `providers.yaml`: everything about
  attachments in one file.
- Masked document text also goes to the local model (a pasted secret's raw text does, for one turn); the file on
  disk keeps the original.
- Activity offers Today / 7 days / 30 days (no custom range yet: carry-over).
- The upload is a raw body, not multipart (no new parser dependency).
- A `.md` or `.txt` file that *starts* with HTML or SVG markup is refused like an HTML file.
